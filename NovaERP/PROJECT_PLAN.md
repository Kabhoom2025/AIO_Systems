# NovaERP — Project Plan, Workflow & Phases

NovaERP is a new vertical inside the `AIO_Systems` multi-tenant monorepo, sitting
alongside `FoodOrderingSystemManagement/`, `PharmacyManagement/`, and
`HRMSManagement/`. It is an enterprise-grade ERP suite (CRM, Sales, Purchase,
Inventory, Manufacturing, Finance, HRMS/Payroll, Projects, Assets, Service
Desk, POS, BI, AI Assistant, etc.), built module-by-module to the standard set
in the original brief. This file is the single source of truth for **how**
NovaERP gets built, in what order, and how each module stays consistent with
the ones before it. Update it whenever the plan changes — do not let it go
stale.

## 1. How NovaERP fits the existing ecosystem

Reuse everything the platform already established rather than reinventing it:

| Concern | Decision |
|---|---|
| Multi-tenancy, orgs, licensing | Delegate to the existing `AIO_Systems` Super Admin service — NovaERP does not build its own tenant/org model. |
| Auth | JWT + refresh tokens issued by `AIO_Systems` Identity, validated by NovaERP.API the same way `HRMS.API`/`Pharmacy.API` do. |
| Routing | All client traffic goes through `ApiGateway` (YARP) on `:5000`; NovaERP.API gets its own route block in `ApiGateway/appsettings.json`, same pattern as the other three services. |
| Clean Architecture layering | `NovaERP.Domain`, `NovaERP.Application`, `NovaERP.Infrastructure`, `NovaERP.API` — mirrors `HRMS.*` / `Pharmacy.*` project shapes exactly. |
| Database | Own database (`NovaERPDB`), EF Core Code First, provider-switchable (PostgreSQL default / SQL Server) via `appsettings.json` — same `EnsureCreated` + seed-on-first-run convention as the other services. |
| Frontend | Angular client at `NovaERP/client/`, standalone components, own port `4204`, lazy-loaded per module. |
| Solution file | `/NovaERP/` folder added to `AIO_Systems.slnx` with the backend `.csproj`s + `NovaERP.Tests`. |
| Docs | Root `README.md` gets a new row in the projects table and a startup step, same as when HRMS/Pharmacy were onboarded. |

Net effect: NovaERP is built as the platform's fifth vertical (fourth backend
service), not a standalone product — it inherits tenancy, auth, gateway
routing, and CI/CD conventions instead of duplicating them.

### Architecture decisions made once real code existed to compare against

Section 1 above was written before any sibling module's actual code had been
read closely. Once Phase 0 scaffolding started, a closer read of
`HRMSManagement` (the most mature, most structurally similar sibling) forced
three corrections to the plan as originally stated:

1. **Repository + Service, not CQRS/MediatR.** None of the four existing
   backend services (`FoodOrder`, `Pharmacy`, `HRMS`, the Super Admin
   `AIO_Systems` itself) use MediatR or CQRS — they all use a plain
   Repository + Service layer with thin controllers. Introducing CQRS for
   NovaERP alone would make it the only inconsistent vertical in the
   platform. Decision: NovaERP uses the same Repository + Service pattern.
   FluentValidation and AutoMapper were still added (lightweight, don't
   change the architecture) since the ERP brief calls for them and they
   don't conflict with the existing pattern — invoked directly in services
   via `ValidateAndThrowAsync`, not as pipeline behaviors (there is no
   MediatR pipeline to hang them on).
2. **Angular 19 + PrimeNG, not Angular 20 + pure Material.** Every existing
   client is pinned to Angular 19 (not 20 — 20 isn't in use anywhere in this
   monorepo yet), and `HRMSManagement/client` and `PharmacyManagement/client`
   both layer PrimeNG on top of Angular Material for tables/dialogs/forms
   (only the Super Admin and Restaurant clients are Material-only). NovaERP's
   client was built as an HRMS-client clone: Angular 19, standalone
   components, PrimeNG (Aura theme) for CRUD tables/dialogs, Material kept
   available but not the primary kit.
3. **New, deliberate additions over the HRMS template** (approved as
   in-scope improvements, not scope creep): FluentValidation, AutoMapper,
   Serilog (console sink, config-driven — HRMS has no structured logging),
   and PostgreSQL ⇄ SQL Server switching via a `DatabaseProvider` config key
   (HRMS/Pharmacy/FoodOrder are Postgres-only). These were chosen because
   they're additive and don't fight the existing pattern, unlike MediatR/CQRS
   which would have required rewriting the whole request pipeline.

`IUnitOfWork` was added as a thin wrapper around `DbContext.SaveChangesAsync`
(not a rewrite of the repository pattern) — most services still save through
their own repository like HRMS does; only one service demonstrates the
explicit multi-repository unit-of-work call, as a seed for later phases where
multi-entity transactions (e.g. a sales order + inventory adjustment) will
need it for real.

### Known limitation surfaced during Phase 1 Slice B verification: `EnsureCreated` does not apply schema changes to an existing database

When the Slice B tables (Settings/FeatureToggle/Currency/ExchangeRate/
Language/OrganizationLanguage/Document) were added, every new endpoint threw
`relation "..." does not exist` on first live smoke test — even though the
build and all 18 tests passed. Root cause: `NovaErpDbContext.Database
.EnsureCreated()` (called on Development startup, same as every sibling
service) only creates the schema when the target database doesn't exist yet;
once `NovaERPDB` existed from Slice A's earlier run, `EnsureCreated` silently
no-opped on the new tables. Fixed for local verification by dropping and
recreating `NovaERPDB` so it regenerated fresh — acceptable for a
dev/demo-only database with no real data, but this is the same limitation
every sibling service (`HRMS`, `Pharmacy`, `FoodOrder`) already has, just not
yet hit because none of them have needed a schema change since their first
run. **Follow-up recommendation for a later phase**: migrate NovaERP (and
ideally the siblings too, though that's out of NovaERP's scope) from
`EnsureCreated` to real EF Core Migrations (`dotnet ef migrations add`) before
this platform has any database anyone cares about keeping — `EnsureCreated`
is fine for early scaffolding but becomes a landmine the moment a schema
change needs to land against data worth preserving.

## 2. Guiding principles (carried through every module)

- Clean Architecture + DDD, Repository + thin Unit of Work, Specification-style scoped queries — **not** CQRS/MediatR (see the architecture-decisions note in Section 1: every sibling service uses Repository + Service, and NovaERP matches them for platform consistency).
- FluentValidation on every Create/Update DTO; AutoMapper for entity↔DTO mapping.
- Every module ships the full vertical slice before moving to the next: schema → entities → DTOs → repository/service → validators → mapper profiles → controller → auth policy → unit + integration tests → Angular model/service/UI/routing/forms/tables → seed data → module README.
- No module is "started" until the previous module's vertical slice is complete and integrated (migrations applied, gateway route added, nav entry added, smoke-tested). This keeps the codebase always in a runnable state and avoids half-finished modules piling up.
- Provider-agnostic EF Core — no raw SQL or provider-specific EF features that break switching Postgres ⇄ SQL Server.
- OWASP Top 10 checklist applied per module (authz on every endpoint, input validation, rate limiting, audit logging of writes).

## 3. Workflow per module (repeated for each module in Section 4)

1. **Design** — ER diagram + entity list + module README stub (what it does, who uses it, how it integrates with modules already built).
2. **Domain** — entities, value objects, enums, domain events in `NovaERP.Domain`.
3. **Application** — DTOs, interfaces (repository/service), FluentValidation validators, AutoMapper profiles in `NovaERP.Application`.
4. **Infrastructure** — EF Core configurations, migrations, repository implementations in `NovaERP.Infrastructure`.
5. **API** — controllers, versioned routes, auth policies/permissions, Swagger annotations in `NovaERP.API`.
6. **Tests** — unit tests (handlers/validators), integration tests (controller + in-memory/test DB) under `NovaERP.Tests`.
7. **Gateway** — add/extend route block in `ApiGateway/appsettings.json`.
8. **Frontend** — Angular feature folder: models, service, standalone components, Material forms/tables/dialogs, charts where relevant, lazy route, nav entry.
9. **Seed data** — realistic sample data for demo/dev, wired into `EnsureCreated` seeding.
10. **Verify** — run module end-to-end through the gateway + UI before marking done; update this plan's status table.

## 4. Phases & module sequencing

Modules are grouped into phases so foundational pieces exist before anything
depends on them (e.g., Approval Workflow Engine and Notification Center are
built early because Sales/Purchase/HR approvals need them).

| Phase | Modules | Why this order |
|---|---|---|
| **0 — Scaffolding** | Solution/project scaffolding (`NovaERP.Domain/Application/Infrastructure/API`), Angular client shell, provider-switchable DB setup, Serilog/OpenTelemetry wiring, Hangfire + Redis wiring, gateway route, CI skeleton | Nothing else can start without the skeleton and cross-cutting infra in place. |
| **1 — Platform foundation** ✅ | Company & Branch Management, User & Role Management (NovaERP-local roles layered on top of AIO_Systems auth), Settings, Localization, Multi-Currency, Multi-Language, Feature Toggles, Notification Center, Document Management, Audit Logs | Every later module needs org/branch scoping, settings, and notifications. |
| **2 — Workflow & automation backbone** ✅ | Approval Workflow Engine, Scheduler, Workflow Automation, Global Notifications (email/SMS/push) | Sales, Purchase, and HR approvals in later phases plug into this engine rather than each rolling its own. |
| **3 — Commercial core** | CRM, Sales, Purchase, Procurement, Tax Engine | The classic quote-to-cash / procure-to-pay backbone; Tax Engine built alongside since both Sales and Purchase need it. |
| **4 — Supply chain** | Inventory, Warehouse, Manufacturing (MRP) | Depends on Sales/Purchase documents (sales orders drive inventory reservations, purchase orders drive stock receipts). |
| **5 — Finance** | Finance & Accounting (GL, AP/AR, bank recon) | Consumes postings generated by Sales/Purchase/Inventory/Payroll — must come after those exist. |
| **6 — People** | HRMS, Payroll, Employee Portal | Payroll depends on Finance (GL posting of pay runs). |
| **7 — Execution & assets** | Projects, Asset Management, Service Desk | Independent of each other; grouped together as the "operations" phase. |
| **8 — Channel** | POS, Retail, Customer Portal, Vendor Portal | Front the commercial core (Phase 3) and inventory (Phase 4) to external users. |
| **9 — Insight & intelligence** | Reporting, BI Dashboards, Analytics, Dynamic Dashboard Builder, AI Assistant | Needs data from all prior phases to be meaningful. |
| **10 — Platform hardening** | API Integrations, Public API, Mobile API, Health Monitoring, System Administration, Backup & Restore, rate limiting, full OWASP pass, perf pass, API versioning audit | Final hardening once the functional surface is complete. |
